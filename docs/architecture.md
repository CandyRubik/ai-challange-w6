# Структура проекта

Backend проекта расположен в app/ и написан на Python с FastAPI.
Точка входа — app/main.py: HTTP API, создание сервисов и раздача интерфейса.
Интерфейс основного чата находится в static/index.html, static/app.js и
static/styles.css.

## Основные каталоги backend

- app/services/chat_sessions.py координирует чат, память, задачу и /help.
- app/orchestration/ содержит продуктовые правила и сборку prompt.
- app/agents/ применяет политики ввода и вывода и вызывает языковую модель.
- app/providers/ реализует Ollama, DeepSeek и выбор модели для каждого хода.
- app/memory/ отвечает за краткосрочную, рабочую и долговременную память.
- app/state/service.py — StateService: чистое преобразование снимка по событию.
- app/services/tasks.py — TaskService: создание, управление этапами и вызовы агента.
- app/memory/service.py — MemoryService: ручная и автоматическая память.
- app/storage/turns.py объединяет сохранение ответа и подготовленной памяти.
- app/storage/ сохраняет чат-сессии, сообщения и задачи в SQLite.
- app/indexing/ загружает README и docs, разбивает их на фрагменты, строит
  E5/FAISS-индекс, ранжирует результаты и проверяет цитаты.
- app/project_help/ отвечает за /help и MCP-инструмент git_branch.

## Хранение данных

История чат-сессий, память и состояния задач хранятся в SQLite.
По умолчанию файл базы — data/chat.sqlite3; путь задаётся CHAT_DB_PATH.
Источники и git-контекст ответа /help сохраняются вместе с сообщением.

Локальные модели E5 и reranker расположены в data/models/e5 и
data/models/reranker. Индекс документации хранится в data/project_index/.
Веса Qwen обслуживает отдельный процесс Ollama. Каталог data/ исключён из Git.

## Проверки и запуск

Тесты backend находятся в tests/. Скрипты подготовки моделей, индексации и
сквозных проверок — в scripts/. Наборы вопросов для оценки — в evaluation/.
Dockerfile и compose.yaml описывают локальный сервис, а deploy/ — приватный
VDS-деплой. GitHub Actions запускает pytest, компиляцию Python и проверку
синтаксиса JavaScript; деплой запускается вручную.

## Изоляция модулей

Три сервиса работают внутри одного процесса. StateService принимает снимок и
типизированное событие, возвращая согласованный новый снимок или ошибку без LLM
и БД. TaskService получает снимок памяти, вызывает агента и StateService.
Цель этапа берётся только из снимка задачи; память предоставляет ограничения
и знания без второй конкурирующей цели.
MemoryService готовит контекст и изменения памяти, сохраняя области чатов.
SQL-соединение используется внутри инфраструктуры записи и не передаётся
через интерфейсы трёх сервисов.

Координатор создаёт отдельный чат при новой цели. parent_session_id связывает
его с исходным; chat_operations связывает устойчивый operation_id с целевым
чатом и сообщением. SQLite атомарно создаёт ветку и операцию до генерации.
После перезапуска повтор обращается к тому же чату. Основная задача и её
рабочая память сохраняются в исходном чате.
