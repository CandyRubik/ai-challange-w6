## Зачем это делать

Опытному инженеру нужен постоянный помощник, который применяет инженерные договорённости проекта к изменениям, замечает реальные дефекты и объясняет последствия. Ценность — меньше рутинного просмотра и повторения одних замечаний. Количество комментариев и абстрактная «оценка качества» не являются целями.

Идея жизнеспособна, если единицей настройки станет проверяемое правило, а результатом — замечание с основанием и контекстом. Свободно сгенерированный «кастомный промпт» без управляемых правил, исключений, проверки доказательств и оценки качества будет постепенно превращаться в источник субъективных советов.

### Ограничение GitHub именно здесь

Репозиторий приватный. На 2026-10-13 API чтения branch protection и rulesets возвращает `403` с требованием GitHub Pro. Поэтому первая версия формирует `pending/success/failure/error` для PR head и показывает причины; принудительное соблюдение потребует доступной защиты ветки отдельно. Комментарий сам по себе ничего не блокирует. [Официальная доступность branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#who-can-use-this-feature).

| Критерий | Проверяемый вопрос | Пример для нашего проекта |

| Запрещённые конструкции | Нарушен ли явный запрет в заданной области? | Передача `sqlite.Connection` через интерфейс доменного сервиса. |

Общие представления модели о «чистом коде» не становятся обязательными правилами. Текущий код — свидетельство реализации и источник примеров; встречающийся в нём паттерн может оказаться существующим долгом. Языковые запреты вроде запрета конкретного Python-оператора требуют отдельного согласования, сейчас такого списка нет.

4. **INV-APPROVAL:** выполнение требует явного утверждения; пересмотр снимает утверждение — `docs/controlled-transitions.md:24`.

8. **INV-RETRY:** одна операция восстанавливает ту же ветку/ход; не создаёт дубликаты — `docs/architecture.md:53`.
9. **INV-REVISION:** запрещённые и устаревшие действия отклоняются до генерации и мутаций — `docs/controlled-transitions.md:77`.
10. **IO-STRUCTURED:** строгие схемы; усечённый JSON не склеивается из продолжений — `app/schemas.py:9`, `app/providers/deepseek.py:195`.

Инварианты корректности проекта описываются отдельно от правил оформления ответов основного чата. Наличие обязательных эмодзи в чате не означает, что AI-отчёт должен состоять из трёх предложений в верхнем регистре.

### Формат профиля

Предлагаемое место — `.ai-review/profile.json`, чтобы использовать stdlib JSON и текущий Pydantic. Версионируются схема, профиль и шаблон prompt.

Каждое правило содержит `id`, категорию, `must/should`, область файлов/символов, требование, причину, источник решения, последствия, положительный и отрицательный пример, способ проверки и явные исключения. Для инварианта дополнительно нужны предусловия, ожидаемое свойство и сценарий нарушения. Обязательность и тяжесть — разные поля.

Правила и нормативные источники читаются из доверенного base. Изменения профиля в самом PR рассматриваются как предложенное изменение политики; они не ослабляют проверку этого PR. Неизвестная версия схемы, противоречащие обязательные правила или отсутствующий обязательный источник дают ошибку конфигурации.

Prompt компилируется детерминированно: общий шаблон → применимые согласованные правила → формат результата → явно помеченные недоверенные данные. Модель не переписывает нормативную часть при каждом запуске.

## Предлагаемая архитектура

Отдельный пакет `reviewer/` и CLI `scripts/review_pr.py`, без HTTP API и собственной БД на первом этапе. Один процесс обработки снимка; GitHub — адаптер запуска и публикации. Интеграционный адаптер может использовать текущий `DeepSeekProvider`; ядро зависит от небольшого интерфейса модели.

```text
PR event / local CLI
  → снимок Git + профиль base
  → применимые правила + deterministic checks
  → retrieval по коду, тестам и документации
  → DeepSeek: кандидаты замечаний
  → проверка evidence + попытка опровергнуть критичные выводы
  → валидированный ReviewResult
  → JSON + Markdown
  → GitHub summary / inline / commit status
```

Порты ограничить реальными внешними зависимостями: чтение снимка репозитория, retrieval, модель и публикация. Сборка prompt, валидация finding и решение о check — обычные функции. Не строить заранее универсальный framework, GitHub App или сервис для нескольких клиентов.

### Воспроизводимый снимок

Зафиксировать repository ID, PR, target branch, `base_sha`, `head_sha`, фактический merge/diff base, хеш diff, профиля и нормативных источников, версии runner/prompt/retriever/model.

Git-объекты читать в отдельном bare repo; head не checkout-ить и не исполнять. Diff считать по зафиксированным объектам с отключёнными external diff/textconv; имена файлов разбирать безопасно, включая пробелы и Unicode. При недостаточной истории найти merge base через ограниченное углубление; при невозможности — явная ошибка.

Семантика PR — изменения от merge base до head. Нормативные правила при этом берутся из актуального base; обе ревизии сохраняются отдельно. GitHub PR diff дополнительно используется для проверки допустимых inline anchors: нельзя обещать, что любой локальный three-dot diff побайтно совпадает с текущим UI.

### RAG по документации и коду

Первый retrieval — по символам, Python AST/imports и тексту документации, без обязательной загрузки E5 в CI. Это именно выбор относящихся к изменению фрагментов перед генерацией, а не передача всего репозитория в один prompt.

- Нормативный корпус: профиль, связанные README/docs/CONTEXT/ADR из base.
- Корпус реализации: изменённые символы, окружающий код, прямые зависимости и связанные тесты из head; прежняя реализация из diff base для сравнения.
- Поддержать Python и ограниченные фрагменты JS/config; для неподдерживаемого синтаксиса применять безопасные окна строк с явной отметкой отсутствия структурного анализа.
- Для каждого изменения обязательно прочитать связанный фрагмент, применимые правила и необходимые соседние контракты. Семантический top-k не заменяет этот обязательный контекст.
- Evidence хранит repository, path, SHA, строки, исходный текст/хеш и роль `normative/base/before/proposed`.
- Источники ограничены allowlist tracked paths. Исключить секреты, `.git`, data, внешние symlinks, submodules и произвольные URL; exclusions видны в отчёте.
- Ограничить объём, глубину зависимостей и число запросов. Если значимый обязательный контекст не помещается, результат частичный и check неуспешен.
- Кеш привязать к снимку и версии retrieval/profile; не использовать общий `data/project_index/active.json` для всех PR.

E5/FAISS/reranker можно подключить через retrieval-адаптер после сравнения качества на том же наборе задач. Для этого отдельно решить доставку фиксированных весов и cache из доверенного workflow; на GitHub runner локальных весов ноутбука нет. Это расширение не требуется для первого RAG-пайплайна.

### Что считается достойным публикации

Finding содержит категорию, rule ID либо нарушенный контракт, тяжесть, происхождение `introduced/worsened/debt`, причинное изменение, условия возникновения, последствия, evidence, рекомендацию исправления и возможный контраргумент.

Обычный код проверяет схему, известность правила, применимость, пути, ревизии, строки, цитаты и совпадение с diff. Для критичного вывода второй проход получает исходные факты и задачу найти контрпример или действующее исключение. Это фильтр ложных замечаний, а не независимое доказательство корректности модели.

Модельная самооценка «confidence=0.99» сама по себе не делает finding блокирующим. Для бага нужен конкретный достижимый сценарий; для нарушения — явное применимое правило и показанное противоречие. Неподтверждённые гипотезы остаются в диагностике. Если неопределённость мешает проверить обязательное правило, итог — незавершённое ревью, а не выдуманный дефект или зелёный check.

По каждому критерию: `pass / violation / inconclusive / not_applicable`. Отдельно: состояние выполнения `complete / failed / cancelled / superseded`, покрытие и ограничения. `pass` означает отсутствие найденного нарушения в указанном покрытии, а не доказательство корректности всей системы.

## GitHub-пайплайн

Предлагаемый триггер — отдельный `pull_request_target` workflow, который исполняет только закреплённую доверенную версию reviewer из default branch. Он нужен для API key и публикации; содержимое PR читается исключительно как данные. Существующий CI тестирует PR своим непривилегированным путём. [Граница доверия GitHub](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

1. На `opened/synchronize/reopened/ready_for_review/edited` проверить PR, target `main` и актуальный снимок. `edited` может менять base/описание; изменения заголовка не должны вызывать ненужную повторную генерацию, если review input прежний.
2. Поставить `AI Review / gate: pending` на **head SHA**. Native workflow на target не считать автоматически проверкой PR head.
3. Отдельные jobs: сбор с `contents: read`; анализ с DeepSeek key без write permissions; publisher с `pull-requests: write`, `statuses: write` и без LLM key. Перед публикацией повторно валидировать переданный JSON как недоверенные данные.
4. Не запускать head-code, его тесты, pip/npm installation, git hooks, `.gitattributes`-конвертеры, submodules, tools и команды из профиля/PR в job с секретами. Не добавлять env/secrets в prompt или сырой prompt в логи. Метаданные не вставлять напрямую в shell.
5. Опубликовать один `COMMENT` review на снимок: summary и batch inline findings. Общие проблемы проекта — отдельный комментарий/раздел с ID долга и влиянием на check; старый код не размечать как новые inline finding.
6. Inline: явно задать `commit_id`, `path`, `line`, `side`. Доказательство может находиться в неизменённом caller, но inline anchor должен указывать на причинное изменение. Если допустимого anchor нет, оставить finding в summary с pinned evidence link.
7. Перед записью сверить head/base/state и generation запуска. Новый head отменяет прежнюю работу. Устаревший запуск не обновляет текущий summary/status; в отчёте всегда указаны SHA.
8. Повтор того же снимка переиспользует публикацию по устойчивому run ID. После неоднозначного ответа POST сначала найти собственный результат, затем повторять. Изменения строк не должны автоматически создавать дубликаты одного finding.
9. Concurrency по PR плюс отдельная сериализация publisher по repository+head+status context. В MVP только target `main`; при двух PR одного head SHA не публиковать конкурирующие success — явно отклонить неоднозначный gate-контекст. Base/profile change при прежнем head создаёт новое поколение результата.
10. Push в main инвалидирует активные результаты, зависимые от прежнего base/profile, и запускает их повторную проверку с ограничением очереди. На первом этапе без merge queue; позже нужен отдельный `merge_group` контракт.

GitHub не даёт атомарного API «опубликовать, только если PR head всё ещё H». Поэтому запись закрепляется за SHA, publisher сериализуется, актуальность проверяется повторно. Краткую гонку между GET/POST нельзя объявлять полностью устранённой; возможный устаревший комментарий явно относится к старому снимку и не должен давать success следующему поколению.

Draft получает явно помеченное отложенное ревью, при `ready_for_review` — полный запуск. Fork/Dependabot, закрытый PR, retarget, конфликт с base, недоступные объекты и API permissions обрабатываются явно. Никаких произвольных загрузок файлов по URL из PR body.

### Результат check

| Условие | Commit status |
|---|---|
| Ревью текущего снимка выполняется | `pending` |
| Полный анализ, нет критичных багов, must-нарушений и активного блокирующего долга | `success` |
| Валидированные критичные баги, must-нарушения или активный долг | `failure` с ID и причинами |
| Ошибка модели/API/схемы, отсутствует существенный контекст, обязательный критерий inconclusive | `error`: ревью не завершено |
| Снимок заменён более новым | Не публиковать актуальный success; управлять только результатом соответствующего поколения |

Рекомендации и noncritical bugs отображаются отдельно и сами не меняют check. Не заменять ошибку на `neutral/skipped`: GitHub может считать их удовлетворяющими required check. [Commit statuses API](https://docs.github.com/en/rest/commits/statuses#create-a-commit-status).

## Долг проекта и решения инженера

Реестр `.ai-review/debt.json` в доверенной base-ревизии хранит ID, правило/контракт, evidence, тяжесть, область, владельца, статус `candidate/active/resolved/waived`, признак блокировки и условие закрытия. В первой редакции активный реестр может быть пустым: наличие старых багов не утверждается без аудита.

Начальный локальный аудит предлагает кандидатов по проекту. Инженер подтверждает активные блокирующие пункты отдельным изменением реестра. В PR активные пункты перепроверяются на head по условиям закрытия; фиксирующий долг PR должен уметь получить success после проверки исправления или явного подтверждения владельца. Тотальный повторный LLM-аудит всего проекта на каждом PR не нужен: проверяется активный реестр и влияние diff, новые кандидаты показываются отдельно.

При принятой политике даже PR с опечаткой получает `failure`, если согласованный активный блокирующий долг остаётся. Это осознанное ограничение, а не неожиданное последствие реализации.

Для оперативного решения использовать доверенный `workflow_dispatch`: PR, head SHA, finding/debt ID, действие, причина, область и срок. Проверять actor по владельцам профиля. Решение сохранять отдельной записью бота с run ID/actor/profile hash/scope; принимать только записи, созданные доверенным workflow, а не скопированный пользователем marker. При повторе оно восстанавливается из журнала PR.

Ложное замечание подавляется для конкретного finding и снимка. Долгосрочное исключение из правила оформляется в версии профиля с path/symbol scope и сроком; оно не должно незаметно распространяться на другой код. Удаление комментария с находкой, её текст или ответ модели не являются решением инженера. Истёкшее/неподходящее исключение не применяется.

## Проверки и оценка качества

Главный шов: `ReviewInput(snapshot, profile) → ReviewResult`. Другая важная граница — publisher, проверяемый через mock GitHub API. Обычные тесты не вызывают платную модель.

- Временный Git repo: three-dot diff, изменённый caller, rename+edit, deletion, force-push, ретаргет, устаревший base, файлы с необычными именами, symlink/submodule/binary и неполная история.
- RAG: обязательное правило и связанный тест действительно попадают в контекст; head-документация не становится нормативной; чужая ревизия/проект не смешиваются; превышение бюджета видно как incomplete.
- Finding: выдуманный rule ID, чужой SHA, отсутствующая цитата, invalid anchor, старый баг без причинного diff, принятое исключение, дубликаты.
- Gate/debt: активный долг даёт failure на несвязанном PR; candidate не даёт; fixing PR снимает активное нарушение по критерию; сбой/неопределённость не дают success; owner decision переживает rerun и имеет scope/expiry.
- GitHub mock: push во время анализа и публикации, два поколения одного head, два PR одного SHA, 403/429, provider timeout, cancel, частичная публикация и POST с неизвестным исходом.
- Prompt injection: code/docstring/PR body требует игнорировать правила, изменить адрес публикации или вывести secret. Проверять отсутствие таких полномочий у модели и отклонение изменённых служебных параметров.

Сформировать минимум 20 размеченных случаев: реальные исправления из истории проекта, намеренно внесённые регрессии инвариантов, чистые рефакторинги и допустимые альтернативы. Отдельно разметить blocked/not blocked, категории и ожидаемые evidence; часть случаев оставить holdout для prompt changes. Исторические исправления `faefa30` пригодны как кандидаты после ручной проверки причинного diff.

Цели калибровки: precision блокирующих finding не ниже 95% на достаточном размеченном наборе, отсутствие блокировок на контрольных чистых изменениях, все заранее выбранные критичные регрессии найдены, повторяемая диагностика неполного анализа. Набор из 20 случаев — старт и средство обнаружения регрессий, статистически он не подтверждает 95% precision в эксплуатации. Публиковать counts и результаты, а не обещать точность по нескольким удачным примерам.

Фиксировать latency, объём контекста, число модельных запросов, расход токенов, coverage, долю отклонённых владельцем finding и стабильность повторов. До автоматического запуска настроить ограниченные время, токены, число вызовов/комментариев и API retries. Превышение лимита даёт incomplete, без молчаливого пропуска файлов.

## Следующий этап: интервью и кастомизация

`ask-matt` — маршрутизатор по навыкам; сам опрос выполняет `grilling`. Установка этого локального навыка у инженера не означает его наличия внутри GitHub Actions. Onboarding и CI-review — отдельные процессы, связанные версионируемым профилем.

Будущий репозиторный skill `project-review-onboarding`:

1. Собирает проверяемые факты о стеке, модулях, CI и существующих документах.
2. Выделяет наблюдения, предположения и инженерные решения; не превращает наблюдения в запреты автоматически.
3. По `ask-matt → grill-with-docs/grilling` задаёт вопросы владельцу, предлагая варианты под обнаруженный стек, последствия и контрпримеры.
4. Проверяет конфликты правил, приемлемые исключения, несколько clean/bad примеров и будущую стоимость соблюдения.
5. Формирует draft профиля и preview prompt по тому же шаблону, который уже работает в MVP.
6. После явного утверждения владельцем сохраняет новую редакцию. При смене стека или значимых правил повторяет только затронутые вопросы.

CI не проводит интервью, не обучает себя новым правилам по комментариям без подтверждения и не зависит от наличия персональных skills на runner. Полный интерфейс интервью в chat-приложении и новая модель пользовательских профилей в MVP не входят.

## Что добавить после MVP

1. **Соответствие задаче:** проверка, реализованы ли заявленные acceptance criteria issue/spec, с указанием непроверенного контекста.
2. **Анализ контрактов:** API/schema/migrations, совместимость, транзакции, race/retry/idempotency, приватность и capability boundaries.
3. **Достаточность тестов:** какие сценарии регрессий остаются непроверенными, вместо требования формального процента coverage.
4. **Feedback и eval:** причины отклонения замечаний, повторные ошибки, регрессии при смене модели/prompt; изменения правил остаются управляемыми.
5. **Локальные правила модулей:** области действия, приоритеты и исключения без размножения конфликтующих глобальных prompt.
6. **Evidence и влияние:** граф затронутых контрактов, callers и тестов; hybrid/vector retrieval только после измерения улучшения.
7. **Аудит долга по запросу:** отдельный полный проход, который предлагает кандидатов; не делает каждый PR поводом для полного переписывания.

Выделение в отдельный репозиторий делать после проверки ядра на втором проекте: переносимый CLI/core, GitHub adapter, schema/templates, eval fixtures и onboarding skill. GitHub App, multi-tenant backend, собственная панель и автоматические исправления — дальнейшие отдельные решения.

## Готовность

Минимум дня 32 достигнут, когда workflow на реальном PR получает закреплённый diff, выбирает относящиеся документы и код и возвращает текст с bugs/architecture/recommendations и evidence. Согласованный MVP дополнительно требует inline, корректного check, активного реестра долга и устойчивых решений владельца; порядок — в [карте PR](decomposition.md).

Карта PR согласована пользователем; первоначальный профиль проверяется на примерах первого среза. Перед включением автоматического облачного запуска нужны DeepSeek secret и результаты калибровки. Принудительный запрет merge отсутствует до отдельного включения поддерживаемой защиты ветки.
