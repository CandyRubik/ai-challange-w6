# GitHub Actions для AI-ревью PR: ограничения и решения

Проверено: **2026-10-13**. Только первичные GitHub Docs. Ниже отдельно указаны документированные свойства и проектные рекомендации; это записка для плана, без изменений workflow.

## Документированные свойства GitHub

### Триггер и граница доверия

- `pull_request` выполняет workflow из merge commit PR; по умолчанию `GITHUB_SHA` — merge commit, а не `head.sha`. Обычные типы запуска — `opened`, `synchronize`, `reopened`; `ready_for_review` нужно добавить явно. При merge conflict этот event workflow не запускает. [Events: pull_request](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request).
- Для PR из fork обычный `pull_request` получает read-only `GITHUB_TOKEN` и не получает остальные secrets; возможно предварительное разрешение запуска maintainer. Dependabot также подпадает под ограничения fork PR. Поэтому LLM API key и возможность публиковать комментарии нельзя считать автоматически доступными. [Events: fork workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflows-in-forked-repositories).
- `pull_request_target` выполняет trusted workflow из **default branch base-репозитория**; default checkout тоже берёт её. Event имеет доступ к secrets и привилегированному token. GitHub прямо предупреждает: нельзя выполнять код недоверенного PR с такими правами; опасны также build/install scripts, конфигурация, зависимости и artifacts из другого workflow. `workflow_run` сам по себе не делает artifact доверенным. [Securely using pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target#risks-of-pull_request_target).
- Для public repos учитывать объявленный enforcement default policy с **2026-11-02**; на дату проверки это evaluate mode. Для private/internal эта default policy не применяется. [Default policy и даты](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target#default-policy-for-pull_request_target).
- `permissions` задаётся для workflow или job; при явном перечислении остальных разрешений они становятся `none`. `checks: write` разрешает создавать check run. Для чтения контента нужен `contents: read`; endpoint ревью требует Pull requests write. Настройки организации могут ограничить write. [Workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions), [Create review permissions](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request).
- Даже title/body/ref/branch name — потенциально недоверенные строки. Подстановка `${{ github.event.pull_request.title }}` непосредственно внутрь inline shell script может дать command injection. [Script injections](https://docs.github.com/en/actions/concepts/security/script-injections).

### Снимок diff и контекста

- `GET /repos/{owner}/{repo}/pulls/{number}` возвращает PR, включая `base.sha`, `head.sha`, `state`, `changed_files`; media type `application/vnd.github.diff` возвращает diff. Endpoint адресует PR по номеру, без параметра «diff на указанной паре SHA». [Get a pull request](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request).
- `GET /pulls/{number}/files` пагинируется: default 30, max 100 на страницу, максимум **3000 файлов** во всём ответе. Есть status, filename, stats, patch в примере. Из query доступны только `per_page`/`page`: endpoint не закрепляет страницы за `base.sha/head.sha`. [List PR files](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files). Переходить следует по `Link: rel="next"`; отсутствие `last` не означает отсутствие следующих страниц. [Pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api#using-link-headers).
- `GET /compare/{BASE}...{HEAD}` поддерживает commit SHA и сравнение в repository network, включая forks. Но список files есть только на первой странице и ограничен **300 файлами** на всё сравнение; пагинация commits этот лимит не снимает. Для binary diff нет `patch`; renamed files имеют `previous_filename`. [Compare two commits](https://docs.github.com/en/rest/commits/commits#compare-two-commits).
- GitHub PR показывает three-dot diff: merge base → topic head. Сравнение текущего base tree с head напрямую имеет другую семантику. Кроме того, GitHub предупреждает, что compare page и PR page иногда используют разные merge bases; нельзя автоматически обещать полное совпадение самосчитанного diff с UI. [Branches: comparisons](https://docs.github.com/en/pull-requests/reference/branches#three-dot-and-two-dot-git-diff-comparisons), [PR versus compare pages](https://docs.github.com/en/pull-requests/reference/pull-requests#differences-between-commits-on-compare-and-pull-request-pages).
- `GET /contents/{path}?ref={commit_sha}` позволяет читать контекст на выбранном commit, иначе default — default branch. API имеет особое поведение для symlink/submodule, лимит directory listing 1000; >1 MB требует raw/object media type, >100 MB не поддерживается. [Repository contents](https://docs.github.com/en/rest/repos/contents#get-repository-content).
- GitHub документирует отдельные ограничения отображения diff: PR — 20 000 загружаемых строк / 1 MB raw diff, один файл — 20 000 / 500 KB, один diff — 300 файлов. Это не заменяет отдельный лимит 3000 у REST PR files. Не найдено оснований считать любой полученный patch доказательством полного покрытия. [Repository diff limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits#diff-limits).

### Публикация и гонки

- Timeline summary публикуется через issue comments API; для PR достаточно **одного** из Issues write / Pull requests write. У create/update comment нет `commit_id`: SHA придётся явно печатать в тексте. [Issue comments](https://docs.github.com/en/rest/issues/comments#create-an-issue-comment).
- Review объединяет body и inline comments. `event: COMMENT` создаёт информационное ревью; есть также APPROVE / REQUEST_CHANGES. `commit_id` нужно задавать явно: иначе API берёт самый новый commit. Review может стать outdated после следующих изменений. [Create review](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request).
- Inline review comment привязывается к `commit_id`, `path`, строке **в diff** и `side`: LEFT для удаления, RIGHT для добавления/контекста; для диапазона нужны start-поля. Старое поле `position` прекращает использоваться. Произвольная строка исходного файла не гарантированно является допустимым anchor. [Create review comment](https://docs.github.com/en/rest/pulls/comments#create-a-review-comment-for-a-pull-request).
- Check run создаётся для конкретного commit (`head_sha`), допускает summary и annotations; максимум 50 annotations на запрос, последующие updates их добавляют. В fork-сценариях нельзя восстанавливать PR association исключительно из `check_run.pull_requests`: документация предупреждает о пустом массиве. [Check runs](https://docs.github.com/en/rest/checks/runs#create-a-check-run), [Update check run](https://docs.github.com/en/rest/checks/runs#update-a-check-run).
- Более простой gate transport — `POST /repos/{owner}/{repo}/statuses/{head_sha}`: `pending`, `success`, `failure`, `error`, стабильный `context`, `target_url` на отчёт. Доступен пользователям/integrations с нужными правами; собственный GitHub App не обязателен. В Actions нужен `statuses: write`. Combined status использует последний status каждого context. API ограничивает 1000 statuses на SHA+context. [Commit statuses](https://docs.github.com/en/rest/commits/statuses#create-a-commit-status), [Actions permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).
- Concurrency group допускает один running workflow/job; `cancel-in-progress: true` отменяет предыдущий running, по умолчанию новый pending заменяет старый pending. Порядок dispatch не гарантирует порядок выполнения. Это управление выполнением, не транзакция «сверить head и записать review». [Concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).
- Для `GITHUB_TOKEN` обычный rate limit — 1000 requests/hour/repository; secondary limits могут сработать при множестве публикаций. Для 403/429 учитывать `retry-after`, `x-ratelimit-reset`, bounded exponential backoff. [REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).

### Настоящий обязательный merge gate и текущий репозиторий

- Required status checks могут быть **checks или commit statuses**. Их нужно включить для целевой ветки через branch protection либо активный ruleset; красный workflow сам по себе merge не запрещает. Required check допускает `successful`, `skipped`, `neutral`: неполный анализ нельзя маскировать последними двумя. Strict mode требует актуальности head относительно base; можно ограничить expected source App и запретить bypass админам. [Protected branches: required checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging), [Ruleset enforcement](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets#using-ruleset-enforcement-statuses).
- На GitHub Free protected branches/rulesets доступны для public repos; для private нужны поддерживаемые платные планы, в том числе Pro. [Доступность protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#who-can-use-this-feature), [Доступность rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets#who-can-use-this-feature).
- **Факт текущей сессии, 2026-10-13:** основной агент выполнил `gh repo view` для `CandyRubik/ai-challange-w6`: `isPrivate: true`. Read-only запросы `GET /repos/CandyRubik/ai-challange-w6/branches/main/protection` и `GET /repos/CandyRubik/ai-challange-w6/rulesets` оба получили **HTTP 403** с текстом `Upgrade to GitHub Pro or make this repository public to enable this feature`. Настройки не менялись. Это API probe текущего repo, а не вывод из документации. **На текущем тарифе нельзя заявить готовый принудительный GitHub merge gate**; реализация status+workflow и включение enforceable required gate — разные acceptance criteria. Публиковать private repo ради этой возможности без отдельного решения нельзя.

## Рекомендации для проектирования — выводы из ограничений

1. **Trusted runner и недоверенные данные разделены.** Reviewer, prompt template, schema, provider credentials и publisher исполняются из закреплённой trusted версии. PR читается как данные. Никаких install/build/test, импорта модулей из head, PR-defined tools, submodule/LFS execution или выполнения artifacts в job с секретами. Для автоматического fork-ревью с LLM key возможен data-only `pull_request_target` при осознанно настроенной policy; обычный fork `pull_request` без отдельного trusted сервиса не имеет нужных secrets. GitHub App/backend — будущая альтернатива, а не обязательная часть Day 32.
2. **Snapshot — явный объект.** Сохранять repo ID, PR number, base/head SHA, фактический diff-base/merge-base SHA, rules/profile hash, index revision, runner/prompt/model versions, hash собранного diff. Не использовать `GITHUB_SHA` как PR head автоматически.
3. **Два способа сбора, разные гарантии.** Для воспроизводимого содержимого предпочтителен fetch immutable Git objects в отдельный bare repo и diff фиксированных объектов; отключить external diff/textconv и не делать checkout head. Для GitHub inline anchors дополнительно использовать текущий PR diff. MVP через PR files API: GET PR до и после всех страниц, сверять пару SHA/состояние и полноту, при изменении пересобирать с bounded retries. Такой bracket снижает риск, но **не является документированной атомарной snapshot API**. Compare SHA...SHA полезен для метаданных/merge base, не как безлимитный files source.
4. **Правила из trusted base.** Профиль, запреты, ADR и нормативная документация берутся на base SHA. Изменения этих файлов в текущем PR — предмет ревью, они не могут ослабить правила для самого себя. Head-код помечается proposed context. Для RAG каждого фрагмента хранить repo/path/SHA/lines/trust-role; shared vector index фильтровать по проекту и revision.
5. **LLM не управляет доверием.** PR body/comments/code/docstrings/retrieved snippets могут содержать prompt injection. Delimiters и system instruction помогают, но не дают гарантии. Нужны ограниченный read-only toolset, отсутствие секретов в prompt, allowlist источников и URL, schema validation результата, проверка evidence/anchors обычным кодом. LLM не должен сам выбирать publisher parameters, API endpoint, исполняемую команду или новые доверенные правила.
6. **Перед публикацией снова GET PR.** При закрытом/merged PR либо изменении head/base результат отмечать superseded и не выдавать за актуальный. Group по repo+PR+workflow, cancellation и повторная проверка сокращают гонки. Между GET и POST всё ещё есть TOCTOU: в рассмотренных comment/review endpoints нет условного «публикуй, только если current head == H». Поэтому review/check закреплять за SHA; не позволять старому job перезаписать общий «последний результат». Один mutable sticky summary требует отдельной сериализации publisher и контроля generation; упрощённый MVP может публиковать summary review на конкретный SHA.
7. **Покрытие — часть результата.** Отдельно показывать reviewed/skipped/truncated/unavailable/context-missing. Пустые findings при неполном анализе не означают «PR чистый». При невалидном inline anchor находку оставлять в summary с evidence link; не выдумывать номер строки.
8. **Публикация идемпотентна на уровне приложения.** Fingerprint по repo+PR+base/head+profile/prompt version, учет уже созданного review/check; retry после network timeout может дублировать POST. После неоднозначного ответа сначала искать собственный результат по идентификатору. Ограничить число комментариев и объединять findings в review.
9. **Вердикт, выполнение и покрытие — разные поля.** По каждому критерию возвращать `pass / violation / inconclusive / not_applicable` с evidence; отдельно `execution: complete / failed / cancelled / superseded` и coverage. Gate — обычный код над валидированным результатом, не свободный ответ LLM: `pending` при старте; `failure` для подтверждённого нарушения блокирующего правила; `error` для недоступного/неполного анализа; `success` только при выполненном договорённом coverage и отсутствии блокирующих findings. Низкая уверенность — `inconclusive`, а не придуманный дефект. Политику ручного разрешения inconclusive/исключений нужно определить явно. Summary+inline можно публиковать как `COMMENT`, обязательность обеспечить отдельным status context.
10. **Status привязан к SHA, не к паре base/head и не к PR.** Старый head не перезапишет status нового head, но два запуска с одинаковым head и разным base/profile могут записать один context, а latest wins. То же относится к двум PR с общим head. Нужны сериализация publisher/generation control и повторная сверка snapshot; минимально ограничить MVP одной target branch и определить поведение при двух PR одного SHA. Native workflow на `pull_request_target` связан с default branch SHA, поэтому отдельный gate status надо явно писать на PR head. После появления поддержки required gate включить strict up-to-date policy; merge queue требует отдельно обработать `merge_group`, это не обычный PR event. [Merge group event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group).

## Corner cases для acceptance/evaluation набора

- Fork и Dependabot; недоступный secret/write permission; требуемое approval; evaluate/enforce event policy; merge conflict; draft → ready; manual rerun; изменения только PR description.
- Head push/force-push или retarget base во время пагинации/LLM/POST; base продвинулся без нового head; два PR одного head SHA; PR закрыли; branch/fork удалён; API object недоступен; canceled job уже успел отправить HTTP request.
- 101, 301 и 3001 changed files; binary, huge/minified/generated files, lockfiles, rename+edit, delete, symlink, submodule, LFS pointer, Unicode/пробелы/управляющие символы в paths; неполная история для merge base.
- PR меняет собственный профиль правил/README/ADR или содержит инструкцию «игнорируй запреты»; RAG выдал чужой проект, старую revision, устаревшую документацию либо существующий плохой код как «пример нормы».
- Finding реальный, но вызван старым кодом; invariant затрагивает неизменённого caller; правило имеет обоснованное исключение; LLM цитирует отсутствующий source; поддерживающий тест/контекст не попал в budget; JSON/anchor невалиден.
- 403/429, provider timeout, context/token budget, частичная публикация, повторный rerun, retry после неизвестного исхода POST, шум из множества одинаковых замечаний. В каждом случае нужен понятный execution/coverage status, а не ложный положительный итог.
