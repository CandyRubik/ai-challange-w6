# AI Challenge W6

Ассистент разработчика с независимыми чатами, задачами и трёхслойной памятью.
Команда /help использует README, docs и текущую git-ветку через MCP.
Рабочая память изолирована по чатам, долговременная память общая.

Агент изолирован от кода на уровне архитектуры: ему передаются системная
инструкция, контекст оркестрации, память и снимок состояния задачи. У провайдера нет tools/function
calling, доступа к файлам, репозиторию, shell или окружению процесса.

## Что внутри

- FastAPI backend и минималистичный chat-first интерфейс;
- память, процесс задачи и мобильная навигация открываются по запросу;
- автомат задач `planning → awaiting_approval → execution → validation → done`
  со строгими переходами, паузой и продолжением;
- редактируемые инварианты ответов: эмодзи, верхний регистр и лимит предложений;
- отдельные чат-сессии с независимой краткосрочной памятью;
- автоматический отдельный чат для новой цели со ссылкой на исходный чат;
- рабочая память для цели, ограничений и решений текущей задачи;
- долговременная память для сведений о пользователе, предпочтений и общих знаний;
- автоматическое извлечение важных фактов и ручные slash-команды;
- исправление рабочей памяти с заменой значений и ссылками на исходные сообщения;
- повтор последнего незавершённого ответа после ошибки или перезапуска;
- SQLite-хранилище всех слоёв, переживающее перезапуск;
- input/output policy для ограничения пользовательского ввода и ответа;
- выбор локальной Qwen через Ollama или облачного DeepSeek в каждом чате;
- выбранная модель обслуживает ответы, память и этапы задач;
- ассистент /help по README и docs: E5, FAISS, reranker и Qwen через Ollama;
- проверенные дословные цитаты, ссылки на файлы и строки и время каждого ответа;
- сохранение провайдера и модели хода для восстановления после ошибки;
- тесты backend, provider и frontend syntax check в CI.

Команда /help подключена к документации через RAG и к текущей git-ветке через MCP.
MCP вызывается оркестратором; модель получает результат как данные.

## Приватный сервис на VDS

Текущий чат и локальная Qwen 3.5 9B Q4 разворачиваются через Docker Compose:
Ollama, FastAPI и Caddy с HTTPS и HTTP Basic Auth. Доступ только владельцу;
введены rate limit, ограниченная очередь и жёсткие пределы контекста/ответа.

Для ручного запуска заполните `deploy/private.env` по образцу
`deploy/private.env.example` и выполните:

```bash
docker compose --env-file deploy/private.env up -d --build --wait
```

Домен должен указывать на сервер, порты 80/443 — быть доступны для HTTPS.
Docker Engine и Compose должны быть установлены на VDS. Для RAG дополнительно
нужны подготовленные веса в `data/models`; индекс README и docs автоматически
строится в `data/project_index`. Обычный чат работает без этих весов.
Для git-контекста MCP нужен настоящий checkout в `PROJECT_ROOT`; rsync-деплой
доставляет документацию без `.git`, поэтому ветка на VDS до подключения checkout недоступна.

В GitHub Actions деплой запускается вручную: **CI → Run workflow → main**,
после backend/frontend-проверок. Настройте repository secrets:

- `VDS_HOST`, `VDS_USER`, `VDS_PORT`, `VDS_DEPLOY_DIR` — подключение и абсолютный путь;
- `VDS_DEPLOY_KEY`, `VDS_KNOWN_HOSTS` — ключ SSH и проверенные ключи сервера;
- `SERVICE_HOST` — DNS-имя для HTTPS;
- `BASIC_AUTH_USER`, `BASIC_AUTH_HASH` — логин и bcrypt-хеш пароля.

Хеш можно получить командой `docker run --rm -it caddy:2.10.2-alpine caddy hash-password`.
Пароль и deployment env-файл в репозиторий не добавляются. Деплой сохраняет
SQLite, веса моделей, TLS-данные и существующие RAG-каталоги.

## Запуск

Требуется Python 3.11+.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
```

Для локального режима запустите Ollama и загрузите модель (интернет нужен
для первоначальной загрузки весов):

```bash
OLLAMA_NO_CLOUD=1 OLLAMA_HOST=127.0.0.1:11434 ollama serve
```

Во втором терминале:

```bash
ollama pull qwen3.5:9b-q4_K_M
```

Новые чаты по умолчанию используют Ollama; ключ DeepSeek для запуска и работы
локального режима не нужен. Чтобы включить облачный вариант в переключателе,
заполните `DEEPSEEK_API_KEY` в `.env`. Затем запустите приложение:

```bash
set -a
source .env
set +a
uvicorn app.main:app --reload --port 8000
```

Откройте <http://127.0.0.1:8000>. История по умолчанию хранится в
`data/chat.sqlite3`; путь можно изменить через `CHAT_DB_PATH`.

В шапке чата выберите **Локальная** или **DeepSeek**. Выбор сохраняется для
этого чата; история, память и прогресс задачи общие для обоих вариантов.
Во время генерации можно выбрать модель для следующего запроса. Уже отправленный
ход и сообщения в очереди сохраняют свой выбор. Кнопка повтора использует
сохранённые провайдер и имя модели, даже после перезапуска приложения.
Ответы LLM подписаны названием модели; служебные вопросы и действия остаются
подписаны «Агент». Старые чаты сохраняют DeepSeek; старым сообщениям название
модели задним числом не присваивается.

Настройки локального провайдера:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_DEFAULT_PROVIDER` | `ollama` | Провайдер новых чатов: `ollama` или `deepseek` |
| `OLLAMA_BASE_URL` | `http://127.0.0.1:11434` | Адрес Ollama, доступный backend |
| `OLLAMA_MODEL` | `qwen3.5:9b-q4_K_M` | Установленная локальная модель |
| `OLLAMA_NUM_CTX` | `32768` | Контекст вместе с резервом под ответ |

Для локальной Qwen thinking отключён. Интервью использует JSON Schema;
остальные структурированные операции — JSON mode и существующую проверку
содержимого. Провайдер ограничивает старую историю по консервативной оценке
размера UTF-8, сохраняя системный prompt и текущий запрос. Если обязательные
данные задачи или память не помещаются, возвращает явную ошибку. Обрезанный
JSON не сохраняется; текстовый ответ может быть продолжен несколькими запросами.
При недоступном Ollama переход в облако выполняется только явным выбором.
Нажмите обновление чата, чтобы повторно проверить доступность локальной модели.

### Проверка локального и облачного провайдера

Сквозной smoke-сценарий проверяет ответ локальной Qwen, переключение на DeepSeek,
очередь сообщений, память и этапы задачи. Результаты конкретных запусков
сохраняются локально в `data/` и не входят в репозиторий.

Реальный прогон без ключа DeepSeek проверяет обычный чат, сохранение и чтение памяти,
планирование, утверждение, выполнение и проверку задачи.
Для повторения запустите отдельную копию приложения с временной базой:

```bash
DEEPSEEK_API_KEY='' LLM_DEFAULT_PROVIDER=ollama \
  CHAT_DB_PATH=/tmp/day27-smoke.sqlite3 \
  uvicorn app.main:app --host 127.0.0.1 --port 8765
```

В другом терминале с активированным `.venv`:

```bash
python scripts/smoke_local_llm.py
```

Этот сценарий создаёт демонстрационный чат, отключает инварианты
в проверочной копии и сохраняет результаты. Запускайте его с отдельной базой.
Для видео с выключенным интернетом заранее загрузите веса, выберите локальную
модель и отправьте новый вопрос; подключения к облачным моделям не требуются.

### Ассистент разработчика: /help и RAG

В основном чате введите `/help` для обзора структуры проекта или задайте вопрос:

```text
/help Где хранятся чат-сессии и память?
/help Как запустить приложение локально?
/help Какая сейчас ветка?
```

Единственный корпус RAG — `README.md` и Markdown-файлы `docs/`. Qwen или явно
выбранный DeepSeek отвечает по найденным фрагментам. Под ответом отображаются
ссылки на файлы, разделы и строки. Цитаты проверяются по исходному тексту;
если сведений недостаточно, ассистент сообщает об этом.

Установите зависимости и подготовьте локальные модели:

```bash
pip install -r requirements-indexing.txt
python scripts/prepare_local_rag.py --source ../ai-challange-w5
```

Скрипт копирует только веса E5 и reranker, затем строит собственный индекс
документации W6. Ранее подготовленные веса можно использовать напрямую:

```bash
python scripts/build_project_index.py
```

Индекс в `data/project_index/` содержит хеши документов. Он автоматически
перестраивается при изменении, добавлении или удалении файла. Веса загружаются
через `local_files_only=True`; для работы нужен подготовленный локальный snapshot.
Если соседний W5 недоступен, укажите `--embedding-snapshot` и `--reranker-snapshot`.

MCP-клиент backend запускает `python -m app.project_help.mcp_server` по stdio
и вызывает `git_branch`. В карточке «Контекст проекта» видны ветка, HEAD,
имя репозитория и время наблюдения. `PROJECT_ROOT` задаёт checkout; по умолчанию
это текущий проект. Ветка читается заново на каждый `/help`, включая повтор после
ошибки. Исторический ответ сохраняет свой снимок, источники и версию индекса.
При недоступном MCP ответ по документации возможен с явной отметкой о ветке.

Команда работает через обычный messages API, доступна сразу и при
активной задаче, сохраняется в истории, но не обновляет память и прогресс задачи.
Сохраняются продуктовые инварианты и выбранная для хода модель.

```bash
python scripts/smoke_project_help.py --base-url http://127.0.0.1:8000
```

[индексация и источники](docs/day28-local-rag.md),
[конфигурации LLM](docs/day29-local-llm.md).

## Новая цель и отдельный чат

Первая цель фиксируется в текущем чате. Другая цель в сообщении или /goal
автоматически создаёт отдельный чат, включая ввод при активной задаче.
Явное создание задачи с другой целью также открывает отдельный чат.
Новая ветка не получает историю, рабочие ограничения или план прежней задачи;
долговременная память остаётся общей. Кнопка «Исходный чат» возвращает к родителю.
Неоднозначное изменение цели вызывает уточнение.

`parent_session_id` хранит происхождение чата. `operation_id` в messages,
создании задачи и ручной записи цели позволяет повторить одну операцию после
ошибки без создания второй ветки. Повтор использует сохранённые модель и разбор
намерения. UI открывает целевой чат и при ошибке генерации; потерянный HTTP-ответ
восстанавливается через состояние операции.

Действие задачи использует снимок памяти на начало действия. Новые ограничения
учитываются со следующего действия; начатый результат сохраняется по своим
параметрам. В обычном чате конфликт изменения рабочей памяти по-прежнему
требует повтора ответа.

Отдельный RAG-чат удалён. При открытии базы повторяемая миграция удаляет только
`rag_chat_turns`, `rag_chat_state` и `rag_chat_sessions`; эти данные не архивируются.
Основной /help продолжает использовать общий индекс, генерацию и проверку цитат.

## API

- `GET /api/health` — состояние backend и наличие ключа DeepSeek;
- `GET /api/models` — настроенные модели и доступность локальных весов/ключа;
- `GET /api/document-index/status` — состояние локального индекса;
- `GET /api/document-index/source?path=README.md&sha256=...` — документ с номерами строк;
- `GET /api/invariants` — общие правила ответов;
- `PUT /api/invariants` — сохранить правила с актуальной `revision`;
- `POST /api/chat/sessions` — создать чат;
- `GET /api/chat/sessions` — список чатов;
- `DELETE /api/chat/sessions` — удалить чаты;
- `GET /api/chat/sessions/{id}` — получить историю чата;
- `PUT /api/chat/sessions/{id}/model` с `provider` — выбрать `ollama` или `deepseek`;
- `POST /api/chat/sessions/{id}/messages` — отправить сообщение; необязательный `operation_id` защищает повтор запроса от дубликатов;
- `GET /api/chat/sessions/{id}/operations/{operation_id}` — найти чат и сообщение операции после потери HTTP-ответа;
- `POST /api/chat/sessions/{id}/task` — создать задачу;
- `POST /api/chat/sessions/{id}/task/actions` — выполнить действие с `action` и `revision`;
- `GET /api/memory?session_id={id}` — получить working и long-term memory;
- `POST /api/memory` — вручную сохранить запись в выбранный слой;
- `DELETE /api/memory/{layer}/{id}` — удалить отдельную запись.

```text
HTTP API → ChatSessionService
            ├── MemoryService → интерпретация и извлечение памяти
            ├── TaskService → StateService (чистый автомат)
            │       └── Agent → PromptBuilder → Ollama / DeepSeek
            ├── /help → документация + MCP
            └── ChatTurnWriter + repositories → SQLite
```

## Разделение кода

- `app/orchestration/` — продуктовые правила и сборка prompt;
- `app/memory/` — сообщения диалога, отдельный `MemoryContext` для working и
  long-term memory, извлечение, дедупликация, API и хранилище памяти;
- `app/state/` — чистый `StateService`, состояния, события и правила переходов;
- `app/services/tasks.py` — `TaskService`: создание и управление этапами задачи;
- `app/storage/` — SQLite-хранилище чат-сессий, атомарная запись сообщений и
  состояния задачи, блокировки и проверка версий;
- `app/services/chat_sessions.py` — координация этих частей и адаптация к HTTP-моделям;
- `app/agents/` — вызов модели, политики ввода/вывода и схемы результатов этапов.

`OrchestrationContext` содержит продуктовые правила ответа. `MemoryContext`
передаёт рабочую память текущего чата и общую долговременную память отдельно
от истории диалога. `TaskContext` содержит только состояние и материалы задачи.
Профилей пользователей и интервью в приложении нет; новый чат сразу готов к работе.

`ChatSessionService` собирает runtime для каждого хода через `ModelRegistry`.
Выбранный провайдер обслуживает ответы, память и этапы задач. Смена модели не
меняет уже выполняющийся ход. Вызовы Ollama идут через backend; браузеру не
нужны CORS-настройки Ollama или доступ к ключу DeepSeek.

[Переход со старой базы без потери истории](docs/workspace-memory.md).

## Инварианты ответов

Пункт **Инварианты** в боковом меню управляет тремя общими правилами для всех
чатов: минимум эмодзи, только заглавные буквы и максимум предложений.
По умолчанию включены все три, лимиты — 3 эмодзи и 3 предложения. Правила можно
отключать и менять лимиты от 1 до 10; пример формата обновляется в меню.
Активные ограничения видны под названием чата.

Правила хранятся отдельно от диалога и памяти. При конфликте ассистент
объясняет отказ и называет правило. Отказ тоже соблюдает формат, не меняет
прогресс задачи и не запускает извлечение памяти. Длинный ответ не обрезается
молча. Настройки переживают перезапуск и очистку чатов; новая редакция действует
на новые запросы.

Описание реализации и правила подсчёта: [инварианты](docs/invariants.md).

## Модель памяти

| Слой | Содержимое | Scope | Запись |
|---|---|---|---|
| Short-term | сообщения диалога | текущая чат-сессия | автоматически при отправке |
| Working | цель, план, ограничения, решения задачи | текущая чат-сессия | автоматически или через slash-команду/API |
| Long-term | факты, предпочтения, устойчивые знания | все чаты | автоматически или через slash-команду/API |

Слои физически разделены в SQLite: `chat_messages`, `working_memory` и
`long_term_memory`. Удаление чатов удаляет short-term и связанную working memory,
но не затрагивает long-term memory.

Перед запросом `PromptBuilder` собирает системную инструкцию, продуктовые правила,
общую долговременную память, рабочую память текущей задачи, ограниченное
окно диалога и новый вопрос.
Записи памяти передаются модели как недоверенные данные, а не как инструкции.
Каждый явный слой ограничен последними 30 записями и 12 000 символов.

Перед ответом отдельный интерпретатор разбирает явно сообщённые пользователем
цели, ограничения, решения, определения терминов и уточнения. Исправление
заменяет прежнее значение; новая цель очищает рабочую память предыдущей задачи.
Неясная отмена вызывает уточняющий вопрос без изменения памяти. Агент получает
предварительный снимок, а новые записи сохраняются атомарно вместе с ответом.

После ответа extraction-запрос сохраняет сведения о пользователе, предпочтения
и устойчивые знания в long-term. Обычные вопросы, догадки модели, секреты и
точные дубликаты не сохраняются. Если интерпретация или extraction недоступны,
чат отвечает с уже сохранённой памятью. У записей, созданных из диалога или
slash-команд, есть ссылка на исходное сообщение.

При ошибке генерации пользовательское сообщение остаётся в истории с кнопкой
«Повторить ответ». Повтор использует сохранённый разбор памяти и не создаёт
дубликат сообщения. Незавершённый ход переживает перезапуск; очередь сообщений
ждёт успешного повтора и остаётся привязанной к исходному чату. Подробнее:
[память и восстановление](docs/chat-memory.md).

Для ручного контроля в поле сообщения по-прежнему доступен autocomplete
slash-команд:

- проект: `/help` — ответы по документации и git-контекст через MCP;
- working memory: `/goal`, `/constraint`, `/decision`;
- long-term memory: `/fact`, `/preference`, `/knowledge`.

Например, `/goal Подготовить демонстрацию` сохраняет цель только для текущего
чата, а `/preference Отвечать кратко` действует во всех чатах.
Команды памяти сохраняются через memory API, отображаются в истории отдельными
карточками и не отправляются языковой модели как сообщения диалога.

Пока агент отвечает, поле ввода остаётся доступным. Новые сообщения попадают в
видимую follow-up очередь, из которой их можно удалить; после завершения ответа
они отправляются последовательно. В чате в это время показывается анимированный
индикатор ответа. Если модель завершила генерацию по лимиту токенов, provider
автоматически запрашивает продолжение и склеивает полный ответ.

## Задачи

Введите цель и требования в поле сообщения и нажмите **Создать задачу**.
Сформируйте и утвердите план, затем выполняйте шаги кнопкой под историей чата.
После формирования задача находится в `awaiting_approval`: выполнение недоступно
до явного утверждения пользователем. Пересмотр плана требует нового утверждения.
Каждое нажатие выполняет одно действие; после последнего шага доступна проверка.
Замечания проверки добавляют шаги исправления, успешная проверка завершает задачу.

Схема над чатом показывает текущий этап, а вкладка **Процесс** справа — цепочку
шагов, критерии и сохранённые результаты. Во время запроса в истории появляется
карточка выполняемого действия с анимацией и временем ожидания. Вкладка **Память**
остаётся доступна; план и управление не перекрывают сообщения.

**Пауза** сохраняет этап, прогресс и ожидаемое действие. Если ответ уже
генерируется, он завершится и сохранится. **Продолжить** снимает паузу, после
чего выполняется сохранённое ожидаемое действие отдельным нажатием. Во время
задачи изменения требований вносятся через **Пересмотреть план**. Готовые
результаты предыдущего плана остаются доступны агенту.

В одном чате хранится одна задача. Для следующей задачи создайте новый чат.
Обычная переписка доступна в чатах без задачи и после завершения задачи.
SQLite автоматически получает новую таблицу `chat_tasks`; прежняя история
сохраняется. Снимок задачи передаётся модели отдельно от обрезаемой истории.
На каждом этапе агент получает рабочую память своего чата и общие знания.
Задачи принадлежат независимым чатам.

Для локального запуска используйте один процесс Uvicorn. В нём параллельное
выполнение одного шага блокируется. Проверка версий в SQLite защищает сохранение
и между процессами, но несколько workers могут одновременно вызвать модель
для одного шага. Пауза действует на границах действий и не отменяет запрос
к провайдеру. При аварийном завершении процесса незавершённое действие можно
повторить из последнего сохранённого снимка.

Описание реализации: [состояние задачи](docs/task-state.md).
Строгие переходы и API отказов: [контролируемые переходы](docs/controlled-transitions.md).

## Проверки

Локальный аудит PR по инженерным правилам проекта:

```bash
python scripts/review_pr.py --base origin/main --head HEAD --format json
```

Профиль берётся из base-коммита, код — из зафиксированных Git-объектов.
По умолчанию проверяются запрещённые Python-импорты. Явный `--semantic` включает
ограниченное DeepSeek-ревью с RAG по коду, тестам и документации; требуется API key
в окружении процесса. Bootstrap, формат профиля и коды выхода:
[аудит PR](docs/ai-review.md).

```bash
python -m pytest -q
python -m compileall -q app reviewer tests scripts
node --check static/app.js
```
